Contract notes for this repo:

- site is one Cloudflare Worker, one R2 bucket (`site-files`) and a Rust CLI. Keep it that way: no accounts, no database, no Durable Objects, no KV, no cron.
- site.stoff.dev serves the homepage and the API only. Every `<label>.site.stoff.dev` URL serves deployed content only, never the API. The domain comes from `SITE_DOMAIN`. Static assets in `public/` are served by the Worker for the apex only (`run_worker_first`), so they never shadow a deployed file.
- A deploy is one HTTP request and one streamed R2 write. The CLI packs everything into one body and the Worker streams it into `d/<id>` through a `FixedLengthStream`, never buffering it and never writing one object per file. An upload needs a `Content-Length`. A malformed or oversized pack is refused before the write, and a body that does not match its declared length fails the write, so nothing is left behind.
- Pack format, both sides change together: the bytes `SITEPACK1\n`, a 4-byte big-endian index length, a UTF-8 JSON index `{"spa":bool,"files":[{"path","offset","length","type","gzip"}],"rules"?:{...}}`, then the file bytes back to back. Offsets are relative to the end of the index, start at 0 and must line up exactly; the lengths must add up to the rest of the body. Paths are relative, use `/`, and have no empty, `.` or `..` segments. The stored object is the pack exactly as sent.
- Encrypted sites (`site dist -e`) are end-to-end encrypted with AES-256-GCM; the CLI (`cli/src/crypto.rs`, `cli/src/pack.rs`) and the browser code (`src/browser/`) must stay byte-compatible, so change both together. The server never sees keys, content types, gzip flags or contents, and there is no encrypted deploy through plain curl because encryption needs the key's private part. File names stay off the server except the address of a page that is opened directly or hard-reloaded, which reaches it as a request path like any URL; the service worker itself never forwards a private path, it answers from a fixed bootstrap path or with a local error. The `/__site/` prefix is reserved on every site, judged on the decoded path with doubled slashes collapsed (`//__site/` and `/%5F%5Fsite/` count) in the Worker and the service worker: public deploys answer it with a plain 404, which is how the service worker learns a name is no longer private and removes itself. The service worker passes only the exact endpoints it uses (`/__site/meta`, `/__site/boot.js`, `/__site/entries/<n>`) to the network, refetching them with `referrerPolicy: "no-referrer"`, and answers every other reserved path, however spelled, and every path whose percent-escapes do not decode, whatever the method, with a local plain 404, so a page's address never reaches the server in `Referer`; the bootstrap page itself is sent with `Referrer-Policy: no-referrer`.
  - Link key: 32 bytes, HKDF-SHA256 with the UTF-8 bytes of the key's private part (the text after the dot, which is never sent to the server) as the secret, an empty salt and info `site link v1 name:<name>` for a named deploy or `site link v1 deploy:<link salt>` for an unnamed one, where the link salt is 16 random bytes written as unpadded base64url (the info uses that text). The link is `https://<label>.<domain>/#<link key as unpadded base64url>`; the link for a name never changes, and any machine with the whole key rebuilds every link (`site ls` prints them).
  - Content key: HKDF-SHA256 with the link key as the secret, a fresh 16-byte content salt per deploy as the salt and info `site content v1`. It is unique per deploy, so nonces are deterministic.
  - Encrypted pack: a normal pack whose clear index is `{"encrypted":{"name":"<name>"|"linkSalt":"<b64url>","contentSalt":"<b64url>"},"files":[{"offset","length"}]}` with no `spa` and nothing in the entries but offsets and lengths; the Worker validates them exactly like a public pack, refuses any other entry field, and allows 5001 entries. Entry 0 is the sealed real index `{"spa":bool,"files":[{"path","type","gzip","length"}],"rules"?:{...}}`, where file `i` is entry `i + 1` and `length` is its stored plaintext length (after gzip). Gzip is decided as for public deploys, before encryption.
  - Each entry is its plaintext in 1 MiB (1,048,576-byte) chunks, each sealed as ciphertext then 16-byte tag; an empty plaintext is one empty chunk, so an entry is `length + 16 * max(1, ceil(length / 1 MiB))` bytes. The 12-byte nonce is the 4-byte big-endian entry number, the 4-byte big-endian chunk index, three zero bytes and a final byte that is 1 on the last chunk, so truncation, reordering and swapping chunks or files fail to decrypt. No associated data. The CLI seals file by file, one chunk at a time, with the ciphertext length known up front for the Content-Length.
  - R2: `d/<id>` and `o/<owner>/d/<id>` also carry `encryptedName` or `linkSalt` as metadata; `files` counts the real files (entries minus one). `/list` returns `encrypted` per deploy (`{"name"}`, `{"linkSalt"}` or `null`) and per name (`true` when it points at an encrypted deploy), and nothing secret.
  - Serving an encrypted deploy: `/__site/sw.js` (the service worker, `Service-Worker-Allowed: /`), `/__site/boot.js` and `/__site/meta` (`{"id","encrypted","entries":[lengths]}`) are sent with `no-cache`; `/__site/entries/<n>` is raw ciphertext with the same caching, ETags and byte ranges as a public file. Every other GET returns the same bootstrap page with `no-cache` and `X-Site-Bootstrap: 1`. `/__site/` is reserved on encrypted sites.
  - The fragment of a link is the key, optionally followed by `#<anchor>` (`/docs/guide#<key>#install`); a fragment that is not 43 base64url characters is an ordinary anchor. The bootstrap page takes the key from the fragment (or IndexedDB, database `site`, store `keys`, entry `link`), checks it opens the sealed index, stores it, registers the service worker for `/`, keeps only the anchor and reopens the page with `location.replace` once the worker controls it. Before reopening in a page the worker already controls, with or without a key in the fragment, it probes the page through the worker at its full address on the current origin, without the fragment, so a path starting with `//` never reads as another host; an answer marked `X-Site-Bootstrap` (a path the worker leaves to the network) ends on a page that says to go home or open the full link again. The tab doing the reopening alone bounds reopens, with one `sessionStorage` record (`site-reopens`: the URL being opened, the reopens tried, when the first was and `history.length`); it allows three reopens of one URL within a minute with no new history entry, and a fourth shows that same page and clears the record, so the next attempt starts fresh. A different URL, a new history entry (another click or outside link) or the minute passing starts a fresh record. The rule never reads the referrer or how long a hop took, and the service worker keeps no per-page state. No key shows the private page; a key that fails shows the wrong-key page and forgets a stored key. The service worker reads the key from IndexedDB, fetches the metadata on every navigation, decrypts the sealed index and serves every path with `resolve` from `src/resolve.ts`, the same rules the Worker uses for public sites, decrypting only the chunks a byte range needs and gunzipping flagged files. When it has no working key it passes the request to the network, so the bootstrap page explains.
  - A navigation whose referrer is not the site itself (a typed or pasted URL, a bookmark, a link from elsewhere, a reload of such a visit) may carry the key in its fragment, which a service worker cannot see, so the worker answers it with the bootstrap page and the status the real page would have; the bootstrap page drops the key and reopens the page from a same-site URL, so the site's own scripts never see the key. Redirects (`/docs` to `/docs/`) are answered first and the browser carries the fragment along. A page that sends no referrer takes this extra hop on every navigation. `<a download>` on a private site downloads the bootstrap page in Chromium and WebKit, whose downloads bypass service workers.
  - Names: a name pointing at an encrypted deploy refuses a deploy without `-e` and a `site point` onto a public deploy; `site point` onto an encrypted deploy works only when that deploy was encrypted for that name. A deploy with `?name=` must carry that name as its hint. Public to encrypted is allowed.
  - The browser scripts are bundled into the Worker by the `browserScripts` plugin in `vite.browser.ts`, imported as `virtual:browser/boot` and `virtual:browser/service-worker`.
- Dot-names: the CLI never packs a file or folder whose name starts with a dot, at any depth and for loose files too, except `.well-known` (`cli/src/dotfiles.rs`). It skips `.git`, `.svn`, `.hg`, `.DS_Store`, `.gitkeep`, `.nojekyll` and `._*` silently and names what else it left out in one stderr line, up to eight names and then a count. The rule applies to names found in a folder walk and to the own name of each loose file; the path the user gives is an explicit request, so the root may be or sit inside a dot-folder (`.vitepress/dist`) and a named symlink is followed. Extensionless files under `.well-known/` get their registered types (`apple-app-site-association` JSON, `webfinger` JRD, `host-meta` XRD, ACME challenges plain text). The Worker has no dot rule, so packs from v0.1.0, v0.2.0 and plain curl serve as stored.
- Path rules (`src/resolve.ts`, the same for public and private sites; an exact file always wins): `//` collapses to `/`; a path tries the file, then `.html`, then `.htm`, and a folder path (`/` or ending in `/`) tries `index.html` then `index.htm`; a folder named without its slash redirects (308) to it, and a page named with a trailing slash redirects to the page, both built from the decoded path the lookup used and keeping the query string (the browser keeps the fragment), and never to the request's own address. After exact names come the same names ignoring letter case and Unicode normalization, like a Mac disk, except that a segment starting with a dot must match exactly, so `/.WELL-KNOWN/x` never reaches `.well-known/x`, and a folded name that two or more files fold to matches none of them. Then a request under an unknown first segment (judged with the same letter case and Unicode rules) whose rest is a file in a subfolder (`/myrepo/assets/app.js` for a build made for a base path, or `/users/assets/app.js` from relative asset URLs on a deep route) serves that file. A route is a path that has no type in the shared content-type table, by its exact path or its last extension (`knownType` in `src/types.ts`; `/users/john.doe` is a route, `/app.js`, `/feed.rss` and `/.well-known/webfinger` are not); routes serve `index.html` with `--spa`, else `200.html` when there is one. Then `404.html` with status 404. Without `404.html`, a deploy whose only page (`text/html` or `application/xhtml+xml`) is `index.html` and that has a script is a single-page app, so its routes serve `index.html`; anything else is a plain 404.
- A body without the magic is a single-file deploy: the Worker writes a one-file index in front of it while streaming, with the type taken from the filename in the URL (`PUT /<filename>`; `POST /` is `index.html`), sniffed from the first bytes like the CLI does when the name has no known type.
- Content types come from one table, `cli/src/types.json`, which the CLI embeds (`cli/src/types.rs`) and the Worker imports (`src/types.ts`); never keep a second copy. A file's exact path is looked up in `paths` first (`.well-known` files without an extension and the root `apple-app-site-association`), then its last extension, lowercased, in `extensions`. The extensions are those of the `mime` package 4.1.2 (built from `mime-db` 1.54.0, the IANA registry plus the Apache and nginx tables; what Cloudflare and GitHub Pages send), with these changes: `ico` and `cur` are `image/x-icon`, `cjs` is `text/javascript`, `vcf` is `text/vcard`, `flac`, `mkv` and `mka` use their IANA types, `hdr` is `image/vnd.radiance`, `data` is `application/octet-stream`, and `gz`, `br` and `svgz` are left out. `text/*`, `application/json`, `application/xml` and `application/*+json` or `+xml` types carry `; charset=utf-8`. A file with no known type is sniffed from its first 512 bytes: any byte the WHATWG MIME Sniffing standard calls binary (0x00-0x08, 0x0B, 0x0E-0x1A, 0x1C-0x1F) makes it `application/octet-stream`, anything else is `text/plain; charset=utf-8`. Nothing is ever sniffed into a type that runs. The type is fixed at deploy time and stored in the pack index, so stored deploys keep the types they were deployed with.
- Charsets (`cli/src/charset.rs` for packs, `src/charset.ts` for single files; keep them in step): a text type keeps `; charset=utf-8` only when the file is valid UTF-8 (a UTF-8 BOM is fine) and does not declare another encoding itself, using the WHATWG HTML prescan of the first 1024 bytes for `<meta charset>` and `http-equiv` content types (skipping the contents of script, style, title, textarea, iframe, xmp, noembed and noframes as Chromium does, and falling back to an XML declaration), a leading `@charset "...";` for CSS and the XML declaration for XML and `+xml` types. A label counts only when it is in the WHATWG Encoding label list, so an unknown or empty label is ignored and the scan goes on; UTF-8 and UTF-16 labels count as UTF-8. HTML and XML that start with `<?x` in UTF-16 without a BOM are not UTF-8. Anything else is stored with no charset, so the browser applies its own order (BOM, the file's declaration, the referring page's encoding, then its default), exactly as from disk. The rule covers every type that carries `; charset=utf-8`: those from the shared table, the sniffed `text/plain; charset=utf-8` fallback, extensionless `.well-known` types and files the CLI decodes from a precompressed copy, which it judges on the decoded bytes. The CLI decides from the whole file; the Worker reads the first 64 KiB of a single-file upload, and only for types that could carry a charset or that it must sniff. Encrypted sites carry the decided type in the sealed index.
- Host rule files: a `_redirects` or `_headers` file at the root of a deploy follows the Netlify and Cloudflare Pages convention. The CLI parses both once, at deploy time (`cli/src/rules.rs`), reports each ignored line once on stderr (at most 10 per file) and never fails a deploy over them; the files stay in the pack but are never served, listed or used as the page at `/`, on any deploy, including ones made by curl or older CLIs; paths resolve as if the two entries were not there (no path rule sees them: names, letter case, the lone page at `/`, single-page app detection, base paths, listings), while file numbers (ETags, encrypted entry paths) still count them. Parsed rules travel as the optional index field `rules`: `{"redirects":[{"from","to","status","force"}],"headers":[{"path","headers":[{"name","value"?}]}]}` (either list may be absent; unknown fields are ignored). It sits in the clear index for public deploys and only inside the sealed index for encrypted ones; the Worker refuses an encrypted pack whose clear index has `rules`, and only the service worker checks sealed rules, so the bootstrap page does not carry that code. The CLI keeps the rules that fit the 2 MB index (redirects first, then header paths, in file order) and reports the rest. `src/rules.ts` holds matching for both the Worker (`route` and `applyHeaderRules` in `src/serve.ts`) and the service worker; it calls `resolve` and its name lookup `findPage`, so path rules stay in one place. The rules read only the `rules` field of the index, so another upload format must carry it in the same places: the clear index of a public deploy and the sealed index of an encrypted one. The Worker refuses a pack whose `rules` are malformed (including patterns that are not well-formed UTF-16 or have more than one `*`), so nothing stored can throw while serving, and, at load time, drops rules a deploy stored by an older Worker might carry malformed. Packs without `rules` behave exactly as before, and the CLI packs a deploy with neither file byte for byte as it did before rules existed.
  - Patterns (`from`, `path`) are decoded paths starting with `/`. Both match the path as `resolve` reads it, in the Worker and the service worker alike: decoded, with doubled slashes collapsed and dot segments already removed by URL parsing, so `//old`, `/%6Fld` and `/x/%2e%2e/old` match `/old`. Letter case counts, as on Netlify ("paths are case-sensitive"), although `resolve` folds it. A segment starting with `:name` (`[A-Za-z]\w*`) is a placeholder matching one non-empty segment, optionally followed by literal text in that segment; one `*` anywhere is a splat matching greedily across segments, with literal text around it in its segment. A trailing slash is ignored on both sides. Matching is linear in the path length: fixed segments are compared from both ends and the splat takes the middle, with no backtracking. Captures fill `:splat` and `:name` in a destination or header value; values are %-encoded. A redirect whose `Location` as sent, with the kept query and, on encrypted sites only, the `#` added to a redirect to another origin, would pass 16,384 characters does not apply; `route` takes `privateSite` and returns the `Location` exactly as sent.
  - Redirects: the first matching rule that applies wins (exact rules are a map lookup, rules with `*` or placeholders are scanned in order); a rule whose destination is refused below does not apply and matching goes on with the next rule. A rule with `force` false gives way when `findPage` finds the path by name (the exact file, `.html`, `.htm`, a folder index, the folder or trailing-slash redirect, the same names folded), as Netlify counts `about.html` and `about/index.html` for `/about`; at `/` that means an index, never the lone page or listing. A forced rule wins over all of it. The fallbacks of `resolve` (the lone page or listing at `/`, base-path assets, `--spa`, `200.html`, `404.html` and the automatic single-page app) come only after every rule, so an explicit rule wins over them. 301, 302, 303, 307 and 308 redirect with `no-cache` and keep the request's query string unless the destination has its own; a destination may be another origin (redirect only). The expanded destination is resolved against the request URL, and one written as a path that resolves to another origin (a capture like `/evil.example` making `//evil.example`) does not match. On encrypted sites a redirect to another origin always carries a fragment of its own (an empty `#` when the rule has none), because browsers copy the request's fragment, which may hold the key, onto a `Location` without one. 200 serves the destination path on this site with status 200 and 404 with status 404, looked up once with `findPage` (following its folder or trailing-slash redirect internally) and never through another rule or a fallback, as Cloudflare Pages applies only the first rule, so a rewrite to a missing page ends in `404.html` with status 404 or a plain 404 rather than `200.html` or an app shell; a 200 rewrite to `/` without an index gets what `/` gets, and a 404 rewrite never answers with a listing. A redirect whose resolved URL is the address requested (same origin, decoded path with doubled slashes collapsed and ignoring a trailing slash, and query) is skipped, so a rule cannot redirect to itself or only add or remove a trailing slash (as on Netlify), and the query is looked for only before `#`. Rule redirects are answered before the path rules' own redirects and the private bootstrap hop. Since those only add or remove a trailing slash, which rules ignore, and rules match letter case exactly, the two never loop together. The CLI drops and reports a rule whose destination is its own path when it keeps the request's query, and rules that redirect in a loop among exact paths it can follow (exact rules before the first rule with `*` or placeholders, honouring `force` against the deployed files with the names `findPage` counts, letter case folded; a path with non-ASCII characters counts as existing, since the CLI does not normalise Unicode, so it never drops a rule the server would let through); other loops end at the browser's redirect limit, and the server never follows rules internally. Default status 302.
  - Headers: every matching rule applies, in file order; repeated names join with `, `, a line without `value` removes what earlier lines or the host set. Rules match the requested path, normalised as above, and apply to every response the path rules make (a file found by any name, `200.html`, the single-page app and `--spa` fallbacks, base-path assets, rewrites, 404 pages, plain 404s, listings and 304s), not to redirects. `FIXED_HEADERS` in `src/rules.ts` (mirrored in the CLI for reporting) can never be set or removed: transport and range headers, `ETag`, `Vary`, `Location`, CDN cache controls, `X-Content-Type-Options`, and every header whose effect reaches past the site's own origin, since all sites share the registrable domain with each other and the API: `Set-Cookie` and `Set-Cookie2` (a cookie for the parent domain would reach every other site), `Clear-Site-Data` (its `cookies` type clears cookies for the whole registrable domain), `Origin-Agent-Cluster` (`?0` asks for a site-keyed agent cluster shared with sibling sites), `NEL` and `Report-To` (policies with `include_subdomains` that outlive the response) and the device-bound session headers `Sec-Session-Registration`, `Sec-Session-Challenge`, `Secure-Session-Registration` and `Secure-Session-Challenge` (they manage cookies and may cover the whole site). `Cache-Control` from a site always gains `no-transform` unless it has that directive; on named hosts it is used only when it has a standalone `no-cache` or `no-store` directive (directives split on commas outside quoted strings, without an argument), so a redeploy shows on the next load; a value with an unclosed quoted string is never used. Custom headers, `Cache-Control` included, add at most 32 KB per response, counted as values expand and with the `no-transform` the host appends; a line that would go past it is skipped. `applyHeaderRules` returns only the names it set or removed, and only those count as decided by the site in `src/cors.ts`.
  - Limits: 10,000 redirects of which 1,000 may use `*` or placeholders, 1,000 header paths and 2,000 header lines, 2,000 characters per line and per value (a destination counted %-encoded, as the CLI stores it). The CLI keeps the first ones and reports the rest; the Worker refuses more.
  - Encrypted sites: the service worker applies the same rules to every response it makes. Headers on the bootstrap page, `/__site/` responses and anything the browser fetches without the service worker (the first visit, hard reloads, requests from other origins) cannot carry them, and `Cache-Control` and `Strict-Transport-Security` mean nothing on responses a service worker makes.
- The CLI gzips html, css, js, json, svg, txt, xml, source maps, wasm and fonts when that makes them smaller. The Worker sends gzipped files as stored with `Content-Encoding: gzip` (`encodeBody: "manual"`) when the client accepts gzip and decompresses otherwise. Raw files support single byte ranges.
- Precompressed build output is handled by the CLI alone, so the pack format, the Worker and the service worker do not change. A `.gz` or `.br` file whose name under the suffix ends in `.js`, `.mjs`, `.wasm`, `.css`, `.html`, `.htm`, `.svg`, `.data`, `.pck`, `.mem` or `.symbols.json`, and any `.unityweb` file (gzip by its magic bytes, otherwise brotli), is decoded and packed under its own path with the inner file's type, exactly as if the decoded file had that name; it is then gzipped like any file, so brotli never reaches the Worker. It must be exactly one complete gzip or brotli stream with nothing after it, or it is packed as it is; one that unpacks to more than 100,000,000 bytes fails the deploy. Every other `.gz` or `.br` is packed as it is, untyped, and arrives byte for byte. A `.gz` or `.br` that decodes to exactly the file beside it without the suffix is left out with a note and does not count toward the file limit; files packed as they are stream from disk and are never read whole. The Worker sends gzipped files as stored with `Content-Encoding: gzip` (`encodeBody: "manual"`) when the client accepts gzip and decompresses otherwise. Raw files support single byte ranges.
- Limits: 100,000,000 bytes per request (under the 100 MB body cap on Free and Pro zones), 5000 files, a 2 MB index, 20 names per key.
- Serving is an index lookup plus an R2 range read. The index (the pack header) is cached in isolate memory and the Cache API, and file bytes in the Cache API, each for 5 minutes, so removals take effect everywhere within minutes. Id hosts send `immutable` to browsers. Named hosts read `n/<name>` from R2 on every request and send `no-cache` with an ETag of `"<id>-<file number>"`. Every deployed response sends `no-transform`, so the edge serves files byte for byte and keeps the ETag; the edge may weaken an ETag, so `If-None-Match` is compared without the `W/` prefix.
- Identity is a random key made by the CLI and kept in its config file, or `SITE_KEY`. It has two parts joined by a dot: `site_<32 characters>` is sent as the bearer token and the server stores only its SHA-256 as `owner`; the 32 characters after the dot never leave the machine and derive the links of encrypted sites. The config file keeps the two parts in separate fields (`key`, `secret`), so v0.1.0, which sends `key` as it is, never sends the private part; a config saved by v0.1.0 has no `secret` and the CLI adds one the first time it runs. The server refuses a bearer token that contains a dot. Only the owning key may repoint, release or delete. The `SITE_TOKEN` secret is for takedowns: it may release any name and delete any deploy, nothing else. Deploys sent without a key are unowned and only `SITE_TOKEN` can delete them. `site key <key>` never drops a different saved key without asking on a terminal.
- R2 layout: `d/<id>` deploy (metadata `owner`, `files`, `size`), `n/<name>` pointer (a random body so every version has its own etag, metadata `id`, `owner`; claimed with `If-None-Match: *`, repointed and released with an etag match; a released name stays as a record with no metadata), `o/<owner>/d/<id>` and `o/<owner>/n/<name>` empty markers for listing.
- A released name stays as a record naming who released it, and only that key can claim it again (nobody, after an admin release or for a record written before this rule), so a name never moves to another owner whose visitors may still run the previous site's service worker.
- Every response from a site host goes through `src/cors.ts`: `OPTIONS` gets a 204 preflight answer (methods GET, HEAD, OPTIONS, the requested headers echoed), and every other response sends `Access-Control-Allow-Origin` (the request's `Origin` with `Access-Control-Allow-Credentials: true`, or `*` without one), `Vary: Origin`, `Access-Control-Expose-Headers` for ranges and ETags, `Timing-Allow-Origin: *` and `Cross-Origin-Resource-Policy: cross-origin`. Sites hold only public files and the Worker never reads cookies, so credentialed reads expose nothing. Other methods get 405. These are defaults, each on its own: `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials`, `Access-Control-Expose-Headers`, `Timing-Allow-Origin` and `Cross-Origin-Resource-Policy` are left as the site decided when it set or removed them in `_headers`. The default `Access-Control-Allow-Credentials: true` goes only with an `Access-Control-Allow-Origin` equal to the request's `Origin`, so the host never pairs it with `*`, and `Vary: Origin` is sent unless the site decided both of those headers.
- Sites share the registrable domain of `SITE_DOMAIN` unless it is on the Public Suffix List, so a site can set cookies for every other site. Storage and service workers stay per origin.
- Deploy ids are 8 characters with at least one digit; names may not have that shape, so the two never collide. Names are 3 to 40 lowercase letters, digits and hyphens, with a reserved list and a brand and credential blocklist matched anywhere in the name (`src/names.ts`).
- The usage rows in `src/pages.ts` are the documentation: the homepage, its hidden descriptions for agents and the text that curl gets come from them. Contact and abuse reports go through GitHub issues; there is no email address anywhere.
- Pages are monospace, monotone and framework-free, with system fonts only, matching keep.stoff.dev and hook.stoff.dev.
- Tests are end-to-end in `tests/e2e` against the real Worker with the real CLI, on `site.localhost` so that `http://<label>.site.localhost:<port>` is a secure context for service workers. Encrypted sites are also tested in headless Chromium with Playwright (`pnpm exec playwright install chromium` once). The navigation suite in `tests/nav` runs every way of navigating a site in Chromium, Firefox and WebKit, each case on a public and an `-e` deploy (`pnpm exec playwright install chromium firefox webkit` once; `NAV_BROWSERS` picks fewer). The `check` script runs the tests with `--max-http-header-size=65536`, so responses near the 32 KB header budget pass the local proxy as they pass Cloudflare. Cover user workflows, not internals. The local dev proxy decodes gzip responses, so tests check that gzip and plain clients get the right bytes, not the `Content-Encoding` header.
